## 后续不同主题怎样组织：问题、运行、作业分开

以下是后续组织约定，不表示旧目录已迁移或所有脚本已经统一接口。

- **研究问题**：例如`FC2-LABEL-01`，回答“训练标签是否取消截断”；wiki只需一条研究记录。
- **一次运行**：固定模型、配方和种子，例如`s-raw-seed42`。S/L、不同标签或不同种子是不同运行；评测运行通过`parent_run`和权重指纹指向训练来源。
- **一次作业**：Slurm分配的一段执行。原配方从30续到60轮，仍是同一次运行，只追加一次作业记录；修复失败后重试也保留前次失败记录。改变学习率、数据或其他实验条件时建立新运行，不能继续写入旧曲线假装只做了恢复。

新主题推荐在运行根目录下使用`<研究问题>/<运行编号>/`，同一运行包含实际生效配置、manifest、指标CSV、检查点、`attempts/`作业记录；评测输出使用独立运行目录。旧日期目录不改名，避免破坏元信息和恢复路径。运行索引把旧、新目录统一起来，无需为了整齐复制文件。

运行根目录的`index.csv`是位置索引，由`tools/hpc/build_run_index.py`读取原有manifest生成。每行是一段作业，字段为研究编号、运行目录、类型、作业ID、父训练目录、manifest路径。同一训练续跑时运行目录相同、作业ID不同；评测失败重试保留各自目录。分数和状态不复制到索引，仍读取原manifest和指标CSV。

`index-sources.json`只登记“哪组目录属于哪个研究问题”，每组登记一次。格式示例：

```json
{"campaigns": [{"path": "20260918-fc2-label01-control", "experiment_id": "FC2-LABEL-01"}],
 "evaluations": [{"path": "20260919-fc2-label01-diagnostics", "experiment_id": "FC2-LABEL-01"}]}
```

收集结果时执行以下命令，再将CSV和sources下载到本机该批结果目录。它不遍历权重，也不修改原始记录。新主题必须先登记其目录；未登记的旧工程测试不自动猜测归属。早期失败记录若没有写出父训练目录，索引留空，以manifest中的启动命令回查。

```bash
python3 tools/hpc/build_run_index.py --runs /path/to/runs --sources /path/to/runs/index-sources.json
```

工程验收使用同样的`checks`登记项，目录结构为`<登记目录>/<验收编号>/manifest.json`，manifest至少包含`job_id`，并保留代码版本、检查结果与日志位置。无需把小测试伪装成训练或另建wiki页。

这是按需执行的收集步骤，没有后台服务，也不会自动改写wiki。

## 小测试代码与正式实验共用什么

新学习率实验使用`run_retrain_experiment.py`和`configs/experiments/`中的配置，支持start/resume/continue。run_lr_stage.py只兼容旧命令；run_campaign.py、run_data_route.py保留用于已有阶段复现，不继续为新参数对照复制它们。公用小型记录写入放experiment_io.py。

## 完整保存与故障恢复

重训器保留`model_*/recovery/`中的最近两组完整保存点，每组包含last与已有best权重、trainer_state和eval_history。写完后才原子切换current.json；评测期间退出时从上一组完整状态恢复，丢弃未完成区间的曲线与临时best。普通checkpoints目录仍供评测和导出，恢复以recovery为准。

旧运行没有recovery时，先检查last权重元信息、状态和曲线的轮次/步数是否一致，进入新代码后建立第一组完整保存点；不猜测或拼接不一致的旧文件。新分支必须使用空输出目录，恢复必须写回同一运行，训练器和启动器均检查。

这是进程中断保护，不替代异机备份。两组完整副本会增加检查点I/O及磁盘占用；保留数量固定为2，待下一次正式运行检查实际开销。临时未发布的一组不会作为恢复起点，下一次成功发布时清理。不要在运行期间手工清理recovery。

训练算法、损失与数据配方没有因此改变。学习率日志只显示生效的调度。空间增强前后截断的次序本次不改，以免改变已登记配方；未来启用空间增强时必须明确选择并单独验收。

## 小测试的保留原则

修改参数使用配置，修改算法使用Git提交，不为每个种子复制Python文件。短跑调用正式训练入口，仅减少步数；其权重必须与正式候选分开。可复用检查保留为`tools/validation/test_*.py`等测试；临时排查命令放已忽略的`tmp/`，结果确认后清理。重复出现的操作再提取成公共函数，不为单次查询建立一个长期脚本。

同主题配置放`EdgeFlowNAS/configs/experiments/<主题>/`。当前label_ab配置有少量重复，这是已运行版本；下一次相关改动可整理共同配置与差异，但每个运行仍保存完整的实际生效配置，不能只留依赖未来默认值的参数差异。

分支按需要独立开发和审查的功能建立，不按GPU、种子或每个作业建立。当前`training/sofia-h200`是连续开发分支；已经被实验引用的提交永久可追溯，不重写其历史。开发功能通过检查后再按用户批准安排合并；不为整理目录擅自合并main。

## GitHub与Sofia的版本关系

本机提交并push → Sofia fetch → 从指定完整提交号创建`MCUFlowNet-releases/<commit>` → 作业使用该固定副本。Git worktree共享Git对象库，工作文件按版本独立；它不是另一套手工维护的代码，也不是容器镜像。

Sofia入口仓库的HEAD可以落后于已fetch的远端分支；实际作业版本由固定副本和manifest决定，不能只看入口仓库的HEAD。已经开始运行的副本不pull、不编辑。相同提交可被多个实验复用，不必每个作业再克隆一份。旧副本只有在无任务使用且版本已在GitHub保存后，才考虑用Git的worktree命令清理，不与训练输出混删。

## 输出保留与同步的最低要求

在Sofia执行的运行，服务器runs是完整输出的原件；本机Runs保留下载的小型结果和登记。wiki只保留支撑阶段结论的必要证据及短判断，不同步逐帧输出或全部日志。数据集和环境放独立共享位置，运行记录引用固定划分/清单与环境指纹，不每个实验复制数据或重新保存一份完整环境。

失败运行保留配置、错误和作业记录；不默认把失败权重当候选。工程短跑的权重可在验收后列为清理候选，但不自动删除。正式训练保留last、各选模标准的最佳、后续分支的起点；重要候选需验证文件完整且可恢复，并另做备份，不能只保存最佳分数。V3训练使用固定文件名覆盖各自版本，Saver设为`max_to_keep=0`，禁止不同选模标准之间自动删文件。若以后改为逐轮新文件名，必须另设明确保留规则，否则文件会不断增加。`tools/validation/test_checkpoint_retention.py`验证真实S/L图的四类保存点跨进程恢复，包括模型、Adam和BN状态。

**GitHub只备份已提交的代码和配置，不备份被ignore的权重，也不备份私人wiki。** 同一Sofia项目中复制检查点可防训练覆盖，但不等于异地备份。权重备份使用`tools/hpc/backup_tree.py`，明确指定来源目录，生成ZIP及逐文件SHA256清单，并读回校验；大目录在Slurm作业中打包。下载到本机`C:/00Work/Backups/MCUFlowNet/`后，再核对ZIP的SHA256。服务器与本机各一份；完成重要阶段时执行，没有后台定时备份。恢复时解压到新目录，通过检查点前缀显式恢复，不能依赖ZIP内旧的绝对路径。

用户已使用Obsidian官方同步管理整个`Lem_brain`，不再另建wiki备份，也不将笔记上传到代码GitHub。Obsidian服务端的版本保留及恢复能力本次未检查。

## 每一部分完成后怎样提交、上传

1. 开始运行前先提交相关代码和配置。记录完整Git提交号，并核对工作区；若仍有改动，保存补丁，不能只写HEAD。
2. 每次运行保存`run_manifest.json`：实验编号、目的、代码提交、配置副本、启动命令、环境/镜像ID、随机种子或不适用说明、输入权重路径和SHA256、数据划分、样本数量、评测方法、输出位置、状态及开始结束时间。
3. 每完成一个可独立核查的部分，检查diff和实际文件清单，再提交并推送当前功能分支。尚未合并的功能不直接推送到main；合并另行安排。
4. 推送成功后记录远端分支和提交；失败则明确记为“已本地提交、未上传”，不得写成同步完成。如果认证需要用户操作，停止后续阶段。
5. 在开始、阶段检查、结束、失败或改变决定时更新实验总表，说明“改了什么、与什么比较、结果怎样、接下来做什么”。必要证据复制到附件并链接，完整日志仍在Runs；重要整理与决定简记wiki维护日志，不记录每轮训练或每次查询。

这种同步是每次进展时明确整理，不是自动把整个Runs目录同步到wiki，也不是把wiki自动推送到代码仓库。

## 一条研究记录可以包含多次运行

例如“FC2训练标签是否应取消截断”是一条研究记录，S/L的截断与原值四组列在同一记录下。续跑、换种子及失败重试保留各自机器运行记录，通过共同研究记录号关联；不为每个作业建立新的wiki页面。普通实验在总表新增一行，必要时补150–300字判断，关键决定留日期和依据。详细结果不因失败或没有收益而删除。

计划页保存设计与验收标准，环境页保存操作方法，实验总表保存状态与结果，文献页保存来源。已有详细证据页只供回查。状态注明核对时间，未查询服务器时不得写成实时状态。agent先读总表相关记录，再按编号读取所需配置、CSV或方案小节；不默认全文加载长篇调研和历史日志。

活跃总表以约4000中文字以内为目标；过长时将已结束阶段归入已有归档，保留摘要链接。未来若增加自动摘要，只更新程序生成的指标区域，保留人工判断；当前没有自动更新wiki或新增跟踪服务。

## 不进入Git的内容

`.gitignore`排除权重、TensorBoard日志、Python缓存、虚拟环境、`.env`及本机配置；根目录的runs/datasets/downloads等意外落入仓库时也排除。已有论文整理结果继续保留，不整体忽略原来的`EdgeFlowNAS/outputs/`。

可复现的实验配置、脚本和小型结果说明应提交。`Dockerfile.local`是可共享的环境定义，明确允许提交。不得为通过ignore检查而强制加入私钥、凭据或大型权重。`.gitignore`不会自动移除已经跟踪的文件，因此每次提交仍需检查暂存清单。

## EdgeFlowNet基线的双口径复测

`tools/validation/evaluate_edgeflownet.py`使用已有845对监控清单和416×1024中心裁剪，遵循EdgeFlowNet的BGR 0–255输入、BN推理模式和输出尺度1。一次预测同时对原始GT及分量截断±50的GT计分；不更改权重或训练标签。`--limit 2`用于恢复与读取验收，正式运行省略该参数。输出目录必须新建，保存manifest、逐样本CSV和汇总结果。

本机示例：

```powershell
./tools/setup/run-local.ps1 python tools/validation/evaluate_edgeflownet.py --checkpoint /runs/pretrained/edgeflownet-archived/best.ckpt --output /runs/BASELINE-EFN-01/edgeflownet-monitor
```

权重来源核验保存在pretrained目录的`upstream-verification.json`，应核对Git blob与固定上游提交，并记录推理代码差异。这项监控集复测不能自动视为论文Table III的6.31复现；原表其他模型的GT与尺寸协议不能由EdgeFlowNet单行倒推。文献转载与共同评测分组展示，避免跨协议排名。
